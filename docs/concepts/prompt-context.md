# Remaining orientation and prompt limits

Status: Idea

## Goal and limit

Besides their tools, actors should know the building blocks that actually exist for their task.
Still open are the concise inventory of capabilities not presented as tools, the verification of
the final driver tool inventory, and some contradictory profile and skill instructions. The
current delivery of the tool overview, detailed contracts, and generated guides is described in
`docs/spec/plugins.md`, `actor-programs.md`, and `typescript-platform.md`; it is not designed
again here.

No second registry, documentation platform, or permission management is created. Existing
metadata, exports, run projections, and skill mechanisms remain the sources. An additional hint
must neither invent a task nor promise a capability that has not been granted.

## Making existing building blocks visible

The initial context should briefly inform about relevant capabilities that are not already
described as concrete tools. For actor programs, template and control names with their purpose
come from the existing metadata or documented exports.
Installed programs and views get their title and existing description from their manifest. Missing
useful descriptions are added at the source, not in a second prompt catalog.

A newly created actor should be able to recognize the existing surfaces relevant to it.
A tool for listing actor programs only describes the access, not the actual inventory.
The overview must not show other actors' prompts, complete states, or source code.
Which views or actions are accessible to the actor must follow from the same identity and
permission check as their actual access.

The inventory is taken from the run at the start of the turn. The existing list tools remain
responsible for changes during a turn; an additional push channel for prompt texts is not
planned. The global coordinator must continue to distinguish regular run building blocks from
its own immediately usable actions.

## Verifying the final tool inventory

What needs to be verified is the end-to-end agreement between the overview generated by the
scheduler and the tools the driver finally registers. The scheduler uses the resolved toolset;
driver, workspace binding, and hooks have further registration points. A static profile catalog
alone does not prove that they agree.

The verification should cover normal actors, exact subsets, workers, dynamic run tools,
workspace tools, and plugin hooks. Functions that are not permitted must neither appear as
available nor become usable through a documentation access. `tools: []` keeps its isolation. If
there is a discrepancy, it has to be fixed in the existing resolution without introducing a
second inventory.

## Cleaning up profile rules and skills

- `ragents.orchestration/orchestration.hbs` should only ask for tools that actually exist. The
  statement that every new agent inherits `actor_input` must take exact tool selection and
  `tools: []` into account. IDs and paths should be accessible through existing handles, short
  references, and server-side resolution; plain prompt prose does not replace missing technical
  reference forms.
- The description of mechanical forwarding must respect the limit of the routing library: it
  takes the last non-empty line of a response. That is not a general forwarding of arbitrary
  multi-line results. The limit belongs in the library description and in suitable examples.
- Explicit skill selection must not additionally preload a complete skill body that is already
  contained in the input. Expansion, preloader, and existing catalog have to be checked together
  against the effective request; no second selection mechanism is created.

## Verification

The existing tests for scheduler, driver, profile composition, and skill preload should cover the
transition to the model request. What matters are the system parts actually sent, the active
schemas, and the selected skills. Production journals do not need a second complete context
database for this.

Acceptance of the remaining work:

- Relevant installed programs and views and building blocks not presented as tools are visible
  concisely and from their actual sources; inaccessible content stays excluded.
- The scheduler overview and the final driver inventory agree, also for exact subsets,
  additional workspace/hook tools, and dynamic run tools.
- Profile instructions contradict neither each other nor the available tool selection.
- Skill bodies are not included twice in the same request with explicit selection and
  preloading.

Only after that can manageable real tasks be compared meaningfully. A model error or a prompt
length alone proves no cause; the structural checks do not replace proof that a concrete model
run actually carried out the domain task.
