    Tailor a workspace for a task

    The script builds the workspace, so the agents start with everything in place.

    • A setup script creates agents, scripts and mini-apps
    • Start it again with one click
    • Ask for inputs before the run starts

    How it works A setup is a tested TypeScript package that appears as a start card. Its script starts agents, TypeScript programs and mini-apps through the same functions the AI uses. A setup dialog can ask for values, such as a repository or a topic, before the run starts.

    Everyone talks to everyone

    Agents write plain text to each other, addressed by handle, such as @agent1.

    • Agents hand work to each other
    • Agents talk to scripts, scripts answer
    • People talk to agents and mini-apps
    • Mini-apps talk to people and agents
    • ... you get the idea :)

    How it works Each agent has its own model, prompt, history and handle. A coordinator takes the task and hands out work. A helper starts with no tools, a picked list, or all tools. When an agent asks you something, the choices appear in the chat and your answer goes back to that agent.

    Agents with their own UI

    People are used to working with interfaces. A UI shows what the agent is doing, and you step in with a click.

    • The AI builds a UI while it works
    • Extensions ship UIs ready to use
    • You and the agent use the same UI and state
    • Your click goes straight to the agent
    • A new UI goes live after its tests pass

    How it works A mini-app is a React view on the state of an agent or a TypeScript program. Its buttons call the program's typed functions directly. The AI type-checks and tests a new view before it goes live; if a rebuild fails, the old version stays active. In VS Code, a mini-app opens in its own editor tab.

    Tools are TypeScript functions

    • Register a typed function once, from your own plugin
    • Agents get it as a tool
    • AI-written code calls it, type-checked first
    • A button calls it without a model
    • Programs call it when events arrive

    How it works A snippet runs once and returns its result to the model. A program keeps its state and reacts to later messages. A setup starts agents, programs and UIs. All of them call the same typed functions, with the same permission checks.

    Event-driven journal

    Every step of a run is an event in the journal. Agents and programs subscribe to the events they care about.

    • An agent starts when another one finishes
    • Replies arrive later as new input, nobody waits
    • A watcher without a model wakes an agent that hangs
    • Agents read the run's journal
    • Fork an agent with its memory

    How it works A subscription turns matching events, such as another agent's finished turn, into new input. A watcher is a TypeScript condition without a model, for example no progress for 120 seconds. Agents query the journal themselves and read other agents' transcripts for handoffs.

    AI or deterministic workflows

    Some work needs judgment, some needs the same steps every time. One run holds both.

    • Let an agent choose the next step
    • Or write the steps in TypeScript, the same every time
    • Mix both in one run: code keeps the order, models do the thinking
    • Code steps cost no tokens
    • Wait for a person when a decision is due

    How it works A setup or an actor program in TypeScript creates the participants and controls the handoffs. Agents fill in the parts that need a model. In the word game, code runs the rounds while four models supply the words.

    Distributed across server and laptop

    Coordinate centrally, and let the tools run where the files are.

    • Runs, agents and models live on the server
    • Laptops and browsers connect to a run
    • Messages flow both ways, live
    • Tools run on the machine that has the files
    • One server, many clients

    How it works The host owns runs, journal, agents, plugins and model access. The workspace executor provides files, shell, Git, processes and language servers, next to the host or on a connected laptop. ragents connect fetches a client profile from the server, and the model relay shares models without revealing providers or keys.

    Pick where each part runs

    Runs, models and tools do not have to live on the same machine.

    • Everything on one machine
    • Everything on the server
    • The server coordinates, your laptop does the work
    • Your runs, the team's setup and models
    • Start here, continue there

    For your teams and your clients

    • Host it on your own server
    • Start a prepared setup with one click
    • Give clients only the setups you approve
    • Hide the technical views, keep chat and UI
    • Share models without handing out keys
    • Several people and agents in the same run Planned

    Use RAgents in your application

    RAgents is a server with one JSON-RPC API. The web interface and VS Code use it, and your product can too.

    • Start the host beside your app, on a private port or over stdio
    • Call the same JSON-RPC 2.0 API as the UI
    • Follow runs live over Server-Sent Events
    • Tailor agents, tools and setups with your own profile and plugins
    • Typed contracts as OpenRPC and TypeScript declarations

    Plugins and profiles

    • A plugin adds tools, skills, prompts and UIs
    • Write your own plugins in TypeScript
    • A profile picks the plugins, models and users
    • A server hands its profile to every laptop

    Drive RAgents from outside

    • Start runs from the command line
    • Let coding agents like Claude Code drive RAgents
    • Send tasks, read the journal, stop a run
    • Scripts get the same JSON-RPC API as the UI

    The same run in the browser and in VS Code

    • No install in the browser
    • Open a mini-app in an editor tab
    • Offer your open folder to a server

    Current status and limits

    RAgents is under active development. Actor programs, their functions, state, and mini-apps belong to one run. Events and time-based triggers need an agent or TypeScript actor. Schedules, a user-management interface, and several people in the same run are not available yet. Profiles may require sign-in or run without it. General user permissions can limit new runs to approved setups and hide settings, models, and technical views while keeping chats and mini-apps usable.
