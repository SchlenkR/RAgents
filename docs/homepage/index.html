Core features

From setup to shared work

A setup brings the building blocks together. Agents handle subtasks, TypeScript defines workflows, and mini-apps make the results interactive.

Setups

  • Assemble a workspace for a task
  • Choose participants and capabilities
  • Reuse a setup for new tasks
  • Start with interfaces ready

A setup combines agents, functions, and mini-apps in one shared workspace and defines how the participants work together. Its structure lives in a TypeScript program, so a prepared setup can be started again for new tasks.

Learn more about setups

Agents talk to agents

  • Delegate tasks
  • Hand off results
  • Communicate with each other
  • Work in parallel

Each agent has its own model, history, and handle, so agents address one another directly, start helpers, and subscribe to events. An AI coordinator decides what happens next, TypeScript programs define fixed handoffs, and every conversation is recorded in the journal.

Learn more about agents

TypeScript as the AI's way of working

  • Combine functions into workflows
  • Run one-off scripts that return results
  • Keep persistent programs with their own state
  • Fixed rules in code, judgment by the model

AI acts in RAgents by writing TypeScript. Functions are the capabilities of the environment, and code is how the AI combines them into reliable steps.

Learn more about TypeScript

Mini-apps

  • Work with AI on the same data
  • See state and agent changes
  • Change it with the right controls
  • Pass your input to the agent

A mini-app is a small interactive interface inside the workspace, such as a list, form, or result view. Humans and agents use the same functions and data, so chat and mini-app become two views of the same work.

The interface

One focused run panel

One piece of work with its participants, files, and results is called a run. Each run opens in one focused panel with a clear, consistent structure.

The selected mini-app and the chat share the main area. Views such as documents, tasks, and diagnostics open from the tab bar and can expand below the chat. In VS Code, a mini-app can also open in its own editor tab.

The same run panel works in the browser and in the VS Code extension, so the structure stays familiar in both places.

Learn to use the run panel

Events and journal

One complete record of every run

  • Trace every step of a run
  • Let results trigger the next step
  • Replay runs without model calls
  • Inspect every code snippet

Every task, response, function call, and state change becomes an ordered event in the journal, and RAgents rebuilds the run by replaying those events. Subscriptions deliver matching events to agents or TypeScript actors as new messages.

An old or damaged journal blocks only the affected run and reports the cause.

Understand events and the journal

Questions and files

Questions, documents, and code

When an agent needs a decision, it can show a question with choices directly in its chat. Your response goes back to that agent so it can continue. Attach files to a chat and reopen them later. Every run has its own document store, shared document view, and task lists.

With a browser configured, agents can open a live web application, fill forms, click controls, capture browser errors, and create real screenshots. The captures remain in the run's documents.

Language servers inspect C#, F#, and TypeScript in the workspace. The diagnostics view shows whether each server is loading, ready, or failed.

Distributed work

Server and workstation form one system

  • Keep coordination central
  • Run project tools where the files live
  • Share models without exposing keys
  • Hand out a profile with its plugin bundles
  • Move a run with its journal

The RAgents host owns the run, journal, agents, plugins, and model access, on a server or on the same machine as the project. The workspace executor provides files, shell commands, Git, processes, language servers, and the browser, beside the host or on a connected workstation.

Plugins reach the workspace only through the run's executor, so the same plugin works unchanged on the server or on a workstation.

A server can also hand its client profile to developers: the profile file and the finished plugin bundles it names. The local host starts them with its own web interface and builds nothing; it only needs the same host API as the server.

Web and VS Code

Two interfaces, the same runs

  • Switch between browser and editor
  • Use the web without installing a client
  • Open mini-apps in editor tabs
  • Offer the open folder as a workspace

The web interface provides the overview, start flow, run panel, chat, mini-apps, and the tab bar. The VS Code extension adds servers, local profiles, runs, and templates to the editor and opens the same run panel, so a run works the same way in both.

Plugins and development

Plugins and profiles

A plugin extends RAgents with typed functions, prompts, skills, views, or other capabilities. AI uses workspace functions directly for files and shell commands, and composes more complex work in one-off TypeScript snippets or persistent actor programs. A profile selects and configures the plugins for a workspace and can also come from another RAgents server. Plugins are built once by their authors into finished bundles; the host loads bundles and never builds plugin sources.

The guide explains the system from the first task through model context, programs, and permissions. The plugin guide explains how to build instructions, workflows, and plugins.

Start a run

Every run starts from the overview. A free-form task opens a chat. A skill can add an editable starter task, reusable instructions, and supporting files. A programmed setup can prepare agents and mini-apps for recurring work.

Install and start

Current status and limits

RAgents is under active development. Actor programs, their functions, state, and mini-apps belong to one run. Events and time-based triggers need an agent or TypeScript actor. Schedules and a user-management interface are not available yet. Profiles may require sign-in or run without it. General user permissions can limit new runs to approved setups and hide settings, models, and technical views while keeping chats and mini-apps usable.

Ideas for future setups

A refactoring setup could combine analysis, implementation, and review. An operational workflow could collect information from connected systems and present it for a decision. These are ideas, not bundled reference workflows.
